# ข้อสังเกตและคำถาม–คำตอบ: MTS Take-home (BOT THB/USD → SQLite)

บันทึกคำถามที่ผมถามระหว่างศึกษาโจทย์ พร้อมคำตอบที่ได้ เรียงตามลำดับที่ถาม
ใช้เป็น context ให้ AI agent และเป็นวัตถุดิบเขียน NOTES.md

---

## สรุปข้อเท็จจริงที่ยืนยันแล้ว

| เรื่อง | ค่าที่ถูกต้อง | ยืนยันจาก |
|---|---|---|
| API ที่ต้องใช้ | Weighted-average Interbank Exchange Rate – THB/USD | โจทย์ข้อ 1 |
| Base URL | `https://gateway.api.bot.or.th/Stat-ReferenceRate/v2` | spec v2.0.1 |
| Endpoint | `GET /DAILY_REF_RATE/` | โจทย์ + spec |
| Query params | `start_period`, `end_period` (รูปแบบ `YYYY-MM-DD`, บังคับทั้งคู่) | spec |
| Auth header | `Authorization: <token>` (ไม่มี `Bearer`) | spec (`securitySchemes`) + หน้า Migration ของ portal |
| โครงสร้าง response | `result.data.data_detail[]` เป็น **array** → `{ "period": "YYYY-MM-DD", "rate": "43.9200000" }` | spec + ยิงจริง |
| ชนิดของ `rate` | **string** ทศนิยม 7 ตำแหน่ง | spec + ยิงจริง |
| ลำดับใน `data_detail` | ใหม่ → เก่า (แต่ยังต้อง sort เอง) | ยิงจริง |
| ช่วงวันที่ต่อครั้ง | **`end - start` ไม่เกิน 31 วัน** เกินได้ 400 | ยิงจริง (ข้อ 17) |
| ช่วงที่ไม่มีวันทำการ | ได้ 200 + `[{"period":"","rate":""}]` ไม่ใช่ array ว่าง | ยิงจริง (ข้อ 18) |
| เวลาประกาศ | ทุกวันทำการ 18:00 น. (เวลาไทย) | spec (ยิง 21:20 น. ได้ข้อมูลวันนั้นแล้ว) |
| Rate limit | ไม่จำกัดโควตารวม, 200 ครั้ง/ชั่วโมง | หน้า product ใน portal |
| Header `X-RateLimit-*` | ใช้ตัดสินโควตาไม่ได้: ยิงผ่านแต่ได้ `Limit: -1`, `Remaining: 0` | ยิงจริง |
| `result.timestamp` | ไม่มี timezone แต่เป็นเวลาไทย (`2026-11-26 21:20:23` ตอนที่ header `Date` เป็น 14:20 GMT) | ยิงจริง |
| Error response | spec เขียนไว้แค่ `200 OK` ไม่มี error สักตัว | spec (ของจริงดูข้อ 19) |

> ยืนยันจากการยิง API จริงแล้วเมื่อ 2026-11-26 (ข้อ 17–23) สรุปเทียบกับ spec: ตรงกับ spec 5 เรื่อง, spec ไม่บอก 4 เรื่อง (จำกัด 31 วัน, แถวว่าง, รูปแบบ error, header rate limit), spec ผิด 2 เรื่อง (`data_detail` เป็น object, ชื่อรายงานเป็นของอีก API)

## คำถาม–คำตอบ

### 1. โปรเจกต์นี้คืออะไร ให้เห็นภาพ
สคริปต์ Python ที่รันแล้วไปดึงเรต USD/THB รายวันจาก ธปท. มาเก็บลง SQLite แล้วแพ็กขึ้น GitHub ให้คนอื่น clone ไปรันต่อได้
Flow: `uv run` → BOT API → แปลงและตรวจข้อมูล (กันข้อมูลซ้ำ) → SQLite
ใน repo ต้องมี CLAUDE.md, README.md, คู่มือ .html และ NOTES.md

### 2. ข้อมูลที่ได้จาก API หน้าตาแบบไหน
JSON ซ้อนกันสามชั้น ข้อมูลที่ใช้จริงอยู่ที่ `result.data.data_detail` เป็น array ที่แต่ละตัวมีแค่ `period` กับ `rate`
ส่วน `data_header` เป็นคำอธิบายรายงาน ใช้ไม่ต้องใช้ก็ได้
- `rate` มาเป็น string ต้องแปลงเป็นตัวเลขก่อน
- ไม่ควรเชื่อว่า array เรียงลำดับมาแล้ว ให้ sort เอง
- ถ้ารันก่อน 18:00 จะยังไม่มีข้อมูลของวันนั้น

### 3. ทำไม rate เป็นรายวัน ไม่วิ่งทุกวินาทีแบบหุ้น
เรตมีสองแบบ
- **Spot rate:** ขยับทุกวินาที ใช้ตั้งราคาหรือเทรดแบบเรียลไทม์
- **Weighted-average reference rate (ตัวในโจทย์):** ธปท. เอารายการที่ธนาคารซื้อขาย USD กันเองซึ่งมีมูลค่าตั้งแต่ 1 ล้านดอลลาร์ขึ้นไปทั้งวัน มาเฉลี่ยถ่วงน้ำหนักด้วยปริมาณ ได้วันละหนึ่งตัวเลข คล้าย VWAP ของทั้งวัน

เรตรายวันมีไว้ให้ทุกฝ่ายอ้างอิงตัวเลขเดียวกัน เช่น งานบัญชี ศุลกากร ภาษี และสัญญา

**ข้อแก้ไข:** ตอนแรกผมคิดว่าข้อมูลนี้ใช้คำนวณราคาทอง ซึ่งไม่น่าใช่ ราคาทองหน้าร้านหรือบนแอปเทรดต้องใช้ spot rate
เรตรายวันของ ธปท. เหมาะกับงาน back office มากกว่า เช่น ตีมูลค่าสต็อกหรือตำแหน่งที่ถือเป็น USD ตอนสิ้นวัน งานนำเข้าส่งออกทอง และรายงานผู้บริหาร → ใช้ใน NOTES ข้อ (a)

### 4. ยิงครั้งเดียวได้ข้อมูลย้อนหลัง 20 วันเลยไหม
ได้ API รับช่วงวันที่แล้วส่งกลับมาทุกวันทำการในช่วงนั้นในการเรียกครั้งเดียว
แต่ 20 วันทำการกินเวลาจริงประมาณ 4 สัปดาห์ และจะนานกว่านั้นถ้ามีวันหยุด (ธ.ค. มีวันหยุด 5 และ 10 ธ.ค.)
วิธีที่ปลอดภัย:
1. ขอข้อมูลย้อนหลังเผื่อไว้ เช่น 45 วัน
2. sort ตาม `period`
3. ตัดเอา 20 ตัวล่าสุด
4. ถ้าได้ไม่ถึง 20 ตัว ให้ log เตือน อย่าปล่อยผ่านเงียบๆ

ไม่ต้องเขียนโค้ดคำนวณวันหยุดเอง

**ข้อแก้ไข (หลังยิงจริง):** ขอ 45 วันในครั้งเดียวไม่ได้ เพราะ API จำกัดช่วงไว้ที่ 31 วัน (ดูข้อ 17) ต้องแบ่งยิงเป็นหลายช่วงแทน

### 5. ยิงซ้ำก็ได้ราคาเดิมใช่ไหม
ใช่ ข้อมูลย้อนหลังเป็นตัวเลขที่ปิดไปแล้ว สิ่งที่เปลี่ยนมีแค่ช่วงข้อมูลที่เลื่อนไปข้างหน้าเมื่อมีวันทำการใหม่
→ คำว่า **"append" ในโจทย์คือกับดัก** ถ้า append ตรงๆ รันสองรอบจะได้ 40 แถว
ทางแก้คือให้ `period` เป็น PRIMARY KEY แล้วใช้ upsert

```sql
INSERT INTO rates (period, rate) VALUES (?, ?)
ON CONFLICT(period) DO UPDATE SET rate = excluded.rate;
```

ผมเลือก upsert แทน `INSERT OR IGNORE` เพราะถ้าแหล่งข้อมูลแก้ตัวเลขย้อนหลัง ข้อมูลของเราจะตามได้ (ยังไม่มีข้อมูลยืนยันว่า ธปท. เคยแก้ย้อนหลังจริง ทำไว้กันไว้ก่อน)
คุณสมบัติที่รันกี่รอบผลก็เหมือนเดิมเรียกว่า **idempotent** → ใช้ใน NOTES ข้อ (b)

### 6. เขาแค่ต้องการให้ดึง rate มาเก็บ SQLite แค่นั้นเหรอ
ถ้าดูแค่ตัวงานก็ใช่ โค้ดน่าจะไม่เกิน 100 บรรทัด แต่โจทย์ง่ายแบบนี้ตั้งใจให้โค้ดไม่ใช่ตัวคัดคน สิ่งที่เขาวัดจริงคือ

| สิ่งที่ส่ง | สิ่งที่เขาดูจริงๆ |
|---|---|
| NOTES.md | เห็นจุดที่โจทย์ไม่ชัดไหม และตัดสินใจอย่างมีเหตุผลไหม |
| CLAUDE.md | ควบคุม AI agent เป็นไหม (JD ข้อ 1) |
| README + คู่มือ .html | ส่งมอบงานให้คนอื่นใช้ต่อได้ไหม (JD ข้อ 2) |
| การสัมภาษณ์ | อธิบายโค้ดที่ AI เขียนได้ไหม |

ไม่ควรทำเกินโจทย์ เช่น dashboard, scheduler หรือ Docker

### 7. `uv sync` / `uv run` คืออะไร ต่างจาก `npm run dev` ไหม
uv รวมหน้าที่ของ npm, nvm และ node_modules ไว้ในตัวเดียว

| uv | เทียบฝั่ง JS |
|---|---|
| `pyproject.toml` | `package.json` |
| `uv.lock` | `package-lock.json` |
| `.venv/` | `node_modules/` |
| `uv sync` | `npm ci` และลงเวอร์ชัน Python ที่ต้องใช้ให้ด้วย |
| `uv add httpx` / `uv add --dev pytest` | `npm install` / `npm install -D` |
| `uv run <คำสั่ง>` | `npx` / `node` แต่จะ sync ให้อัตโนมัติก่อนรัน |

`npm run dev` เรียก script ที่ตั้งชื่อไว้ใน `package.json` ส่วน `uv run` รันคำสั่งอะไรก็ได้ในสภาพแวดล้อมของโปรเจกต์
ถ้าอยากได้ชื่อสั้นๆ ให้ประกาศ entry point ใน `pyproject.toml`
โหลด `.env` ได้ด้วย `uv run --env-file .env ...` โดยไม่ต้องลง `python-dotenv`

### 8. ไม่ควรเก็บไฟล์ .db ไว้ใน `.venv` ใช่ไหม
ถ้าเป็นงานจริง ไม่ควร `.venv` มีไว้เก็บ library เท่านั้น ลบแล้วสร้างใหม่ได้ตลอด เทียบฝั่ง JS ก็คือ **การเก็บฐานข้อมูลไว้ใน `node_modules`**
ที่ที่ถูกคือ `data/` ที่ใส่ไว้ใน `.gitignore`
**แต่ในข้อสอบนี้ให้ทำตามโจทย์** เพราะเขาอาจมีเหตุผลหรือมีระบบตรวจอัตโนมัติ ให้ตั้ง default ตามโจทย์ ให้เปลี่ยน path ได้ผ่าน `BOT_DB_PATH` แล้วเขียนเหตุผลไว้ใน NOTES

### 9. ข้อไหนในโจทย์บอกให้เก็บใน `.venv`
ตารางข้อ 1 แถว **"ปลายทาง"**: "append ลง SQLite ชื่อ bot_api_daily_{ชื่อผู้สมัคร_Eng}.db วางไว้ใน .venv ของ project"
พอดูคู่กับข้อ **2.2** ที่ให้แนบไฟล์ .db มาทางอีเมล จึงน่าจะเป็นเพราะ `.venv` อยู่ใน `.gitignore` อยู่แล้ว ไฟล์ข้อมูลจะไม่หลุดขึ้น repo สาธารณะ → เชื่อมสองข้อนี้ใน NOTES ได้

### 10. ถ้าเขา clone ไปรันเอง ข้อมูลของเขากับของเราจะเหมือนกันไหม
- วันที่ตรงกัน → เรตเหมือนกัน
- ช่วงวันที่เลื่อนตามวันที่รัน → มีแค่บางช่วงที่ทับกัน
- รันก่อนหรือหลัง 18:00 → วันล่าสุดอาจต่างกัน
- `fetched_at` → ต่างกันแน่นอน

นี่อธิบายได้ว่าทำไมข้อ 2.2 ให้ส่งไฟล์ .db ที่ได้จากการรันจริงมาด้วย ใช้เป็นจุดตรวจได้ว่าวันที่ทับกันต้องมีเรตตรงกัน ถ้าไม่ตรงแปลว่า parse ผิดหรือ timezone ผิด

### 11. ตารางใน db มีคอลัมน์อะไรบ้าง
ชุดขั้นต่ำที่เสนอ:

```sql
CREATE TABLE IF NOT EXISTS rates (
    period      TEXT PRIMARY KEY,   -- 'YYYY-MM-DD' เรียงตามตัวอักษรแล้วได้ลำดับตามวันที่
    rate        REAL NOT NULL,      -- หรือ TEXT (ดูด้านล่าง)
    fetched_at  TEXT NOT NULL       -- ISO8601 +07:00
);
```

**ต้องตัดสินใจเอง:** `rate` จะเป็น REAL (คำนวณใน SQL ได้ ความแม่นยำราว 15 หลัก พอสำหรับ 7 ทศนิยม) หรือ TEXT (ตรงตามต้นทาง 100% แต่ต้อง CAST ทุกครั้งก่อนคำนวณ)
ตั้งใจไม่ใส่: `currency_pair`, `source`, ตาราง log การรัน → เกินขอบเขตโจทย์

### 12. ควรยิง API ดู response ก่อนเขียน CLAUDE.md ไหม

### 15. ใน product มี API หลายเส้น ต้องใช้เส้นไหน
โจทย์ระบุไว้แล้วว่าใช้ `DAILY_REF_RATE` เส้นเดียว
API ตัวเดียวแบ่งเป็นสี่เส้นตามความถี่ คือ DAILY, MONTHLY, QUARTERLY และ ANNUAL
**ระวัง:** spec แรกที่โหลดมาเป็นของ API อีกตัว (Average Exchange Rate, `Stat-ExchangeRate`) ไม่ใช่ตัวที่โจทย์ต้องการ ให้ดูที่ path `/Stat-ReferenceRate/v2/DAILY_REF_RATE/` เป็นหลัก

### 16. ExchangeRate กับ ReferenceRate ต่างกันยังไง

| | ReferenceRate (ตัวที่ใช้) | ExchangeRate |
|---|---|---|
| ซื้อขายระหว่างใคร | ธนาคารกับธนาคาร (interbank) | ธนาคารกับลูกค้า |
| คำนวณจาก | รายการ ≥ 1 ล้าน USD เฉลี่ยถ่วงน้ำหนักด้วยปริมาณ | ค่าเฉลี่ยอัตราที่ธนาคารพาณิชย์ประกาศ |
| สกุลเงิน | USD อย่างเดียว | 19 สกุล |
| ฟิลด์ | `rate` ตัวเดียว | `buying_sight`, `buying_transfer`, `selling`, `mid_rate` |
| เทียบได้กับ | ราคาขายส่ง | ราคาหน้าเคาน์เตอร์ (มีส่วนต่างซื้อขาย) |

**เอกสารของ ธปท. มีจุดผิด** (ใช้ใน NOTES ได้):
- spec ของ ReferenceRate ค่าตัวอย่าง `report_name_eng` เป็นชื่อรายงานของ ExchangeRate
- spec ของ ExchangeRate ค่าตัวอย่าง `api` เป็นชื่อของ ReferenceRate
- `data_detail` ของเส้นรายวันประกาศชนิดเป็น `object` แต่ตัวอย่างเป็น array (response จริงเป็น array)
- spec ไม่ได้บอกเรื่องจำกัดช่วง 31 วัน และเรื่องแถวว่างตอนไม่มีข้อมูล (ข้อ 17, 18)

**ยิงจริงแล้วพบว่า** `report_name_eng` ใน response จริงก็เป็นชื่อรายงานของ ExchangeRate เหมือนกัน แปลว่าบั๊กอยู่ที่ระบบของ ธปท. เอง ไม่ได้ผิดแค่ในเอกสาร → ยิ่งเป็นเหตุผลว่าไม่ควรใช้ `data_header`

→ ยึด response จริงเป็นหลัก ไม่เชื่อ spec อย่างเดียว

### 17. ยิงจริงแล้วเจอว่าขอได้ไม่เกิน 31 วันต่อครั้ง
ขอ 45 วันแล้วได้ 400

```json
{"httpCode":"400","httpMessage":"Bad Request","moreInformation":[{"message":"Exceed limit period. Limit period is 31 days"}]}
```

ไล่หาขอบแล้ว: `2026-10-26 → 2026-11-26` ผ่าน แต่ `2026-10-25 → 2026-11-26` ไม่ผ่าน แปลว่า `end - start ≤ 31 วัน`
ช่วง 31 วันนั้นได้ 24 วันทำการ แต่ถ้าช่วงไหนวันหยุดเยอะ อาจได้ไม่ถึง 20 เช่นปลายธันวาถึงต้นมกรา (วันหยุด 5/7, 10, 31 ธ.ค. และ 1 ม.ค.)

แนวทาง:
1. ยิง 2 ช่วงต่อกัน แต่ละช่วงไม่เกิน 31 วัน (ครอบคลุมราว 60 วัน)
2. รวมผล ตัดแถวว่างทิ้ง (ข้อ 18) แล้ว sort ตาม `period`
3. ตัดเอา 20 ตัวล่าสุด ถ้าไม่ถึง 20 ให้ log เตือน

ยังห่างจาก rate limit 200 ครั้ง/ชั่วโมงมาก → ใช้ใน NOTES ได้ เป็นตัวอย่างว่า spec ไม่บอก ต้องรู้จากการยิงจริง

### 18. ช่วงที่ไม่มีวันทำการ API ไม่ได้ส่ง array ว่างกลับมา
ขอช่วง 2026-11-21 ถึง 2026-11-22 (เสาร์อาทิตย์) ได้ **200** พร้อมข้อมูลแบบนี้

```json
"data_detail": [{"period": "", "rate": ""}]
```

### 19. Error แต่ละแบบหน้าตาเป็นยังไง

| กรณี | HTTP | Body |
|---|---|---|
| ไม่ส่ง `Authorization` | 401 | `{"error": "Authorization field missing"}` |
| key ผิด | 403 | `{"error": "Access to this API has been disallowed"}` |
| วันที่ผิดรูปแบบ (`2026/11/01`) | 400 | `moreInformation[].message`: `Parameter: start_period format must be yyyy-mm-dd` |
| start มากกว่า end | 400 | `Parameter start_period must not be greater than end_period` |
| ช่วงเกิน 31 วัน | 400 | `Exceed limit period. Limit period is 31 days` |
| ไม่ส่ง params เลย | 404 | `{"Message": "No HTTP resource was found ..."}` (เผยชื่อ host ภายใน) |

error แต่ละแบบใช้คนละรูปแบบ (`error` / `httpCode` + `moreInformation` / `Message`) โค้ดจึงควรตัดสินจาก status code แล้วค่อยแนบ body ไว้ใน log ไม่ควร parse body เพื่อหาสาเหตุ

- 400 ทุกกรณีใช้รูปแบบเดียวกัน ข้อความอยู่ที่ `moreInformation[0].message`
- ไม่มี key ได้ 401 แต่ key ผิดได้ 403 ควรแยกข้อความ log สองกรณีนี้ให้คนอ่านรู้ว่าต้องแก้อะไร (ยังไม่ได้ตั้ง `BOT_API_KEY` / key ใช้ไม่ได้หรือยังไม่ได้รับอนุมัติ)
- ไม่ส่ง params ได้ 404 แทน 400 และ `Message` ใช้ตัว M ใหญ่
- สร้างวันที่ด้วย `date.isoformat()` ก็จะไม่เจอ 400 รูปแบบวันที่

เพิ่มเติม: `Authorization: Bearer <token>` ก็ได้ 200 เหมือนกัน แต่ให้ยึดแบบไม่มี `Bearer` ตาม spec

### 23. ผลการทดลองเปลี่ยนแผนอะไรบ้าง
กฎที่ได้สำหรับโค้ด (รายละเอียดที่ agent ต้องทำตามอยู่ใน `CLAUDE.md`)

1. ยิงเป็นช่วงละไม่เกิน 31 วัน 2 ช่วงต่อกัน แล้วรวมผล (ข้อ 17)
2. กรองแถวที่ `period` หรือ `rate` เป็นค่าว่างทิ้งก่อนทำอย่างอื่น (ข้อ 18)
3. sort ตาม `period` เอง ตัดเอา 20 ตัวล่าสุด ถ้าไม่ครบ 20 ให้ log เตือน (ข้อ 4)
4. บันทึกด้วย upsert โดยมี `period` เป็น PRIMARY KEY ห้าม append ตรงๆ (ข้อ 5)
5. ตัดสินผลจาก status code: 401 คือไม่ได้ตั้ง key, 403 คือ key ใช้ไม่ได้, 400 ให้ log `moreInformation` (ข้อ 19)
6. ห้ามใช้ header `X-RateLimit-*` ตัดสินโควตา (ข้อ 22)
7. ไม่ใช้ `data_header` ใช้แค่ `data_detail` (ข้อ 16, 21)
8. header เป็น `Authorization: <token>` ไม่ใช่ `X-IBM-Client-Id` และไม่ต้องมี Bearer (ข้อ 13)
